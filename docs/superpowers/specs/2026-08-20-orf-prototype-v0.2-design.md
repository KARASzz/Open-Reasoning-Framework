# ORF 原型文档 v0.2 升级设计

> 本 spec 记录对 `Open_Reasoning_Framework_Prototype_v0.1.md` 的融入式升级设计。
> 产出物为 `Open_Reasoning_Framework_Prototype_v0.2.md`，v0.1 保留，git 历史即版本记录。

## 背景

v0.1 原型文档定位清晰（可调用、可组合、可审计、可证伪的推理算子库），但存在八处内部张力：Operator 执行语义未定义、认知差模块游离于架构外、框架清单自相矛盾、Cross-Audit 机制空白、Selector 无选择依据、交互模型未定义、评测无 ground truth、语言策略缺失。经逐项讨论，形成以下八项决议，并落实为 v0.2 的章节级修订。

## 八项决议总账

| # | 张力点 | 决议 |
|---|---|---|
| ① | Operator 本质 | 类型化转换器；护城河 = Schema 校验 + 编排纪律 + 契约强制 + 评测回归（引擎四层论） |
| ② | 认知差无架构位置 | 定位为执行组合器（Combinator），与 Framework、Operator 并列为三类可调用单位 |
| ③ | 第 7/14 节框架清单矛盾 | MVP 维持 8 框架；补写激励结构、权力关系定义 + 相邻框架边界判据；博弈移入长期扩展 |
| ④ | Cross-Audit 机制空白 | 并行单轮 + 攻击契约 + 综合硬规则 |
| ⑤ | Selector 无选择依据 | LLM 选择 + 强制结构化理由，Runtime 校验 3～7 数量边界 |
| ⑥ | 交互模型未定义 | 无状态再分析（prior_analysis + new_evidence，仅重审受影响假设） |
| ⑦ | 评测无 ground truth | 专家盲评验证核心假设 + 渐进 golden 变量集做回归 |
| ⑧ | 语言策略 | Schema 字段采用 localized map 结构，MVP 只填中文 |

## 架构核心变化（v0.2 §2、§5、§6）

### 三类可调用单位

取代 v0.1 的两层原子结构：

1. **Framework（分析框架）**：分析镜头。新增边界判据字段——"我回答什么 / 我不回答什么"。
2. **Operator（推理算子）**：类型化转换器，`(类型化输入 → 类型化输出)`。LLM 是负责填空的推理引擎，算子本身声明输入/输出对象类型（参与者、主张、证据条目、假设等）。
3. **Combinator（执行组合器）**：执行组合模式。首个实例为认知差分析：立场参数化执行 + 结构化 diff。

### 推理图取代自由文本

一次分析累积为带溯源的类型化对象图（事实/假设/证据/冲突）。v0.1 §22 的审计要求（哪些事实来自用户、哪些是模型推断、哪些框架冲突）成为推理图的天然属性，不再是额外机制。

### 引擎论证（写入 §2）

核心类比：SQL 语句本身只是文本，但数据库不是"文本文件集合"——让 SQL 有价值的是引擎、约束和事务。同理，Operators 是推理的查询语言，Runtime 才是引擎。"不是 Prompt 仓库"的论证从口号升级为四层机制展开：

1. **Schema 校验**：结构正确性强制；
2. **编排纪律**：选择、并行、对抗角色指派；
3. **契约强制**：输出缺字段即拒绝重跑，攻击者不得沉默；
4. **评测回归**：对基线的持续对照。

## 运行机制变化（v0.2 §9、§11、§12、§13、§17）

### 核心运行流程（§9）

```text
用户输入（可携带 prior_analysis + new_evidence）
↓
问题重述 → 区分事实/假设/推理/价值判断 → 问题类型识别
↓
Framework Selector（LLM 选择 + 强制理由，Runtime 校验 3～7 边界）
↓
并行执行各框架 Operators（产出类型化对象，累积进推理图）
↓
Cross-Audit（并行单轮攻击 → 证伪过关）
↓
Synthesizer（硬保留规则综合）
↓
结构化输出 + 完整审计日志
↓
（可选）用户补充证据 → 携带 prior_analysis 再调用，仅重审受影响假设
```

### Cross-Audit（§11）

- **并行产出**：各框架结论同时生成，攻击者互不可见，切断结论沿链传染（串行链是风险四"框架互相证明"的温床）。
- **攻击契约**：每次攻击必须产出至少一项实质攻击（冲突 / 反例 / 替代解释 / 推翻条件），或明确声明"无实质攻击"并附已检查项清单。两种结果都进审计日志——既防止编造噪声攻击，也防止默认沉默。
- **证伪过关**：每个重大假设必须带可推翻条件，否则不得进入综合。
- **综合硬规则**：Synthesizer 不得把仍有未被反驳竞争假设的局面合并成单一结论；"证据不足，无法判断主因"是一等合法输出。
- **轮次**：MVP 固定单轮，不迭代（多轮对话天然向收敛漂移且成本翻倍）。

### Framework Selector（§17）

- 机制：LLM 直接选择，输出契约 = `问题类型标签 + 框架列表（3～7）+ 每个框架一句话命中理由`；
- Runtime 校验数量边界；
- 选择理由对用户可见、可质疑，并进入审计日志——选择理由本身就是可被纠正的对象。

### 认知差组合器（§12）

从"应用模板"改写为架构单位：

- 输入：问题 + 立场 A + 立场 B；
- 执行：同一组 Operator 分别按立场执行；
- 输出契约（固定六项）：共同事实 / 双方解释 / 冲突点 / 潜在原因 / 需统一概念 / 保留的合理差异。

### Runtime 新增组件（§17）

- **Model Adapter**：LLM 接入抽象层。成功标准 5（"不同 LLM 接入后保持基本推理结构"）的实现前提——换模型只换 adapter，编排与契约不变。

### 输出协议（§13）

六层结构保留，补两点：

- Selector 的选择理由作为第 0 层展示（可质疑的入口）；
- 第 2 层"核心假设"允许以"竞争假设集 + 证据不足声明"形态出现。

## 内容与结构变化（v0.2 §7、§8、§14、§16）

### 首批框架内容（§7、§14）

- 补写**激励结构**、**权力关系**两个框架的第 7 节级详细定义（思想来源、核心问题、典型问题）；
- **博弈框架**从 §7 移入 §24 长期扩展，MVP 清单维持 8 个，消除两节矛盾；
- 每个 Framework 新增边界判据："我回答什么 / 我不回答什么"，重点为利益↔激励、角色↔权力两对相邻框架写明分界；
- MVP 总量维持 60～100 个高质量 Operators。

### Operator Schema 重写（§8）

- `inputs` / `outputs` 类型化声明（引用对象类型：参与者、主张、证据条目、假设等）；
- 文本字段采用 localized map 结构（如 `name: {zh: "收益风险不对称"}`），MVP 只填中文；
- `boundary_criteria`（边界判据）、`counterexamples ≥ 2`、`failure_conditions` 保持强制；
- 输出契约四件套不变：`hypothesis / evidence / uncertainty / next_validation`。

### 目录结构（§16）

- **operators 并入 frameworks**：取消独立 `operators/` 树，算子放在所属框架目录下（如 `frameworks/incentive_structure/operators/`），消除双树漂移；
- `runtime/` 下新增 `adapter/`（Model Adapter）；
- `schemas/` 增加 `combinator.schema.json`。

## 评测体系地基化（v0.2 §18）

### 阶段一：专家盲评（服务 §28 核心假设验证）

- 成对比较、隐藏输出来源、附评分维度（对应 §18.2 指标：覆盖率、反例能力、证据意识、可证伪性、多路径能力、行动价值、稳定性）；
- 对比四基线：裸 LLM 零样本 / 大型系统提示词 / 单一 Framework / 多 Framework + Cross-Audit。

### 阶段二：渐进 golden 变量集（回归资产）

- 从核心测试案例起，每案例由 2～3 位专家**独立**预标注"已知重要变量清单"，保留分歧不强行合并；
- 覆盖率指标落地为对 golden 集的召回率；
- 分工：盲评出结论，golden 集防回归，两者不互相替代。

## 风险与治理修订（v0.2 §25、§21）

- 风险一"退化成 Prompt 仓库"的处理从"强制 Schema 和测试案例"扩写为引擎四层论；
- 版本治理不变，但明确：Schema 字段结构（localized map、类型声明）属破坏性变更范畴，升级须走 §21 的变更记录流程。
